# React Migration Audit

Date: 2026-08-07

## Current frontend architecture

`apps/web` is a framework-free browser client. It uses ES modules, string-template views, direct DOM event binding and a custom repository that loads all server state. The API and database are already production systems and remain authoritative for ledger, balances, limits, reversals, recurrence and investment-sale integrity.

The frontend is organized with iOS-inspired folders, but most interaction orchestration is concentrated in `src/App/main.js` and most server-state orchestration in `src/Data/LiveFinanceRepository.js`. Feature view files return HTML strings. Dialog markup lives in `public/index.html` and is populated imperatively.

## Current folder structure

- `public/index.html`: full application shell, authentication forms and all dialogs.
- `src/App/main.js`: bootstrap, route rendering, form/dialog state, event binding, mutations, CSV export and user-facing error mapping.
- `src/App/Router.js`: hash router for dashboard, transactions, accounts, savings, upcoming, reports and settings.
- `src/App/AppContainer.js`: constructs configuration, session store, API client and finance repository.
- `src/Networking/APIClient.js`: central fetch client, normalized errors, refresh-token rotation and a shared in-flight refresh promise.
- `src/Persistence/SessionStore.js`: `localStorage` session persistence under `defterx.live.session`.
- `src/Data/LiveFinanceRepository.js`: book bootstrap, aggregate refresh, DTO-to-view mapping and all mutations.
- `src/Features/*`: string-template views for each page.
- `src/DesignSystem/tokens.css` and `app.css`: global tokens and the existing responsive visual system.
- `src/DesignSystem/icons.js`: SVG strings hydrated into placeholders.
- `worker/index.js`: Cloudflare runtime config, health endpoint and static asset forwarding.
- `scripts/build.mjs`: copies public/source files, bundles `main.js` with esbuild and emits `dist`.
- `scripts/check.mjs`: JavaScript syntax checks.
- `scripts/smoke-live.mjs`: CDP-driven Microsoft Edge production E2E.

## Entrypoint and routing

`public/index.html` loads `/config.js`, global CSS and bundled `/app.js`. `main.js` creates a singleton container, checks health/session, initializes data and renders into `#app-content`.

Navigation is hash based (`#/dashboard`, `#/transactions`, `#/accounts`, `#/savings`, `#/upcoming`, `#/reports`, `#/settings`). Hash routing currently preserves back, forward, refresh and direct links. The React migration should keep these URLs with `HashRouter` to avoid an unnecessary user-facing URL change. Cloudflare already has `not_found_handling: single-page-application`.

## Build and deployment

- Current web build: custom Node copy script plus esbuild.
- Deployment: `wrangler deploy`, static assets from `apps/web/dist`.
- Runtime public config: `/config.js` generated by the web Worker from `APP_DISPLAY_NAME`, `APP_ENV` and `API_BASE_URL`.
- No secret is exposed to the browser; the API URL and display/environment values are public configuration.
- Target build: Vite emits `dist`; Wrangler continues serving that directory and the Worker continues owning `/health` and `/config.js`.

## Current dependencies

The web workspace has only Wrangler as a declared development dependency. It has no React, Vite, TypeScript, router, component-test library or lint stack. The monorepo already uses TypeScript and Vitest in other workspaces, and Zod exists in the API. React, React DOM, React Router, Vite, the React Vite plugin, Zod, TypeScript, ESLint and focused component-test dependencies are justified for the target.

## Global state approach

`LiveFinanceRepository.state` holds user, book, accounts, categories, transactions, transaction opening balance, upcoming records/filter, dashboard, cash-flow range/visibility/account selection, reports and all investment entities. The application mutates this object and rerenders whole pages.

Target classification:

- Global/auth state: session and authenticated user.
- Shared server state: active book plus the finance snapshot needed across routes/dialogs.
- Page client state: transaction filters, cash-flow toggles/account selection, open dialogs and form drafts.
- No Redux-class store is required. React context plus feature hooks is sufficient for the current scale.

## Authentication approach

The current API client stores access and refresh tokens in local storage, retries one authenticated request after a 401 and shares one refresh promise across concurrent failures. Refresh failure clears the session. Logout attempts server revocation and always clears local state.

This behavior must be preserved exactly. The React auth provider should subscribe to central session changes, prevent stale authenticated UI after refresh failure and avoid refresh loops. Backend rotation and reuse protection must remain unchanged.

## API client and error approach

The current central client supplies the base URL, auth header, JSON handling, network normalization, one refresh retry and at most two retries for safe GET requests returning 5xx. It currently has no abort signal parameter or runtime response validation.

The React client should retain these semantics, add optional `AbortSignal`, use typed errors, and validate critical auth/account/transaction/investment responses with Zod. Feature components must call feature API modules rather than raw `fetch`.

## CSS and design approach

The existing UI uses global class names and CSS variables. It is responsive at 1050, 760 and 440 pixel breakpoints. Tables intentionally use horizontal containers at narrow widths. The dashboard cash-flow chart is a fixed-viewBox SVG with overlay tooltip, not a chart library.

Migration priority is visual parity. Existing token values and global layout CSS can be reused first, then located under `src/styles`. React markup should retain established class names. No Tailwind or component framework is warranted.

## Behavior and edge cases that must be preserved

- A blank dialog can close without browser validation; validation occurs only on submit.
- Server errors appear inside the active dialog, not behind it.
- Income/expense has one account; transfer alone exposes a target and rejects identical accounts.
- Mutations disable duplicate interaction and refresh authoritative server state only after success.
- Transaction deletion/correction and sale deletion/correction are server reversal workflows, never client balance edits.
- Running balance and opening carry come from the API for selected accounts.
- Date-only inputs are posted at local noon to avoid a one-day timezone shift.
- CSV begins with a UTF-8 BOM and neutralizes spreadsheet-formula prefixes.
- Used accounts/categories/types are archived/deactivated rather than destructively disappearing from history.
- Cash-flow month subtraction is calendar based; zero bars are omitted; hover does not resize or scroll the graph.
- Investment-sale UI must not update optimistically before the server has completed reversal/replacement.

## Migration risks

1. Reimplementing ledger or running-balance meaning in React instead of displaying API results.
2. Losing the single shared refresh promise and triggering backend refresh-token reuse protection.
3. Rendering a route before book/bootstrap data is available or keeping stale data after logout.
4. Date-only values shifting through UTC conversion.
5. Dialog errors/focus moving behind native dialogs or cancel buttons accidentally submitting.
6. React rerenders causing chart tooltip jitter or resetting account/series selections.
7. Client-only filters diverging from API-backed account/date filters and CSV contents.
8. A large all-at-once view component reproducing the current `main.js` concentration.
9. Vite and Worker runtime configuration diverging between local and production.
10. E2E selectors changing without preserving equivalent user-observable behavior.
11. Current transaction endpoint returns at most 1000 records; large-data pagination is a post-migration concern, not a reason to rewrite the API now.
12. `README.md` references an `apps/ios` directory not present in this checkout; documentation must describe the actual tree.

## Backend boundary

No financial schema migration is required. The browser continues to call the Cloudflare API Worker, which reaches Neon through Hyperdrive. Double-entry mapping, entry persistence, balances, limits, idempotency, reversal, recurrence and investment-sale integrity stay in the API/database layer.
